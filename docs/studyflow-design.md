# StudyFlow: Technical Design (Hackathon v1)

**Audience:** founder/builder. **Status:** draft v1. **Day boundary timezone:** Africa/Lagos (UTC+1, no DST).

## 0. Summary

Friends form a small invite-only group (3 to 8 members). Each member studies their own subject and topic in a timed session, either LIVE (group start at a server-held time) or SOLO (any time). After the session, a 15-question MCQ quiz on that member's topic, generated by a local LLM, closes the session. Three group mechanics drive retention: a daily group streak with freezes, a shared goal per live session, and a weekly group bar filled by personal-best points. Nobody is ever ranked on raw quiz score across subjects.

**Stack:** Next.js + Tailwind (PWA) | FastAPI | SQLite via SQLModel/SQLAlchemy + Alembic | fastapi-users (email + password, JWT) | Ollama (local LLM) | APScheduler (nightly jobs) | WebSockets (presence).

**Conventions:** all timestamps stored in UTC. `lagos_date(ts)` = calendar date of `ts` in Africa/Lagos (use `zoneinfo`). Week = Monday 00:00 to Sunday 23:59:59 Lagos; `week_start` = the Monday date. Rounding: `round()` below means round half up (`floor(x + 0.5)`), not Python's banker's rounding.

## 1. Scoring rules

### 1.1 Definitions

- **Planned duration** `P`: one of 25, 45 or 60 minutes (chosen when the session is created). Capping at 60 keeps late-night sessions inside the nightly job window (section 2).
- **Active time** `A`: seconds counted by the server from presence heartbeats (section 3.3). The client clock is never trusted.
- **Required time** `R`: `0.8 * P` for SOLO and on-time LIVE joiners. For late LIVE joiners see 3.1.
- **Completed session:** `A >= R` and quiz submission meets both deadlines in 3.10. Infrastructure unavailability follows 3.7. A missed quiz deadline retains time-only completion and base points when `A >= R`, without quiz/improvement points or a baseline entry (decision, 15 Oct 2026).
- **Session date:** `lagos_date(session.started_at)` for that participant. A session started at 23:40 counts for that day even if the quiz is submitted after midnight.
- **Quiz score** `S`: percentage correct, `100 * correct / 15`.

### 1.2 Points per completed session

| Component | Symbol | Formula | Range |
|---|---|---|---|
| Base | `B` | `round(P / 3)` -> 25 min = 8, 45 min = 15, 60 min = 20 | 8 to 20 |
| Quiz | `Q` | `round(S / 10)` | 0 to 10 |
| Personal-best improvement | `I` | `clamp(round((S - baseline) / 5), 0, 10)` | 0 to 10 |
| Live bonus | `L` | `+5` if the session was LIVE and the user joined on time (<= 10 min late) | 0 or 5 |
| Group full-live bonus (v2) | `G` | `+5` each if every eligible group member completes the same live session | 0 or 5 |

`session_points = B + Q + I + L + G` (max 50).

Additive bonuses were chosen over a multiplier: they are easier to explain, easier to show as ledger lines ("+5 live bonus"), and do not amplify quiz score differences between subjects.

### 1.3 Baseline (per user, per subject, per level)

- Key: `(user_id, subject_norm, level)`. `subject_norm` = lowercased, trimmed, alias-mapped ("maths" -> "mathematics", "chem" -> "chemistry").
- `baseline` = mean `S` of the user's **last 3** counted quiz attempts for that key, *before* the current one.
- **First quiz rule:** 0 prior attempts -> `I = 3` flat ("welcome" points) and this attempt seeds the baseline. 1 or 2 prior attempts -> baseline = mean of those.
- Changing level starts a new baseline (new key). Quizzes marked unavailable (3.7) never enter the baseline.
- Improvement is never negative. Deliberately tanking a quiz to lower the baseline costs roughly as many `Q` points as it later gains in `I`, and `I` is capped at 10, so it is not worth gaming.

### 1.4 Daily cap

Only the user's **first 3 completed sessions per Lagos day** earn points. Further sessions still count for streaks and the live session goal but write a `0` ledger entry with reason `daily_cap`. Daily maximum is therefore 150 points per user.

### 1.5 Weekly totals, group bar and leaderboards

- Weekly reset: Monday 00:00 Lagos. Nothing is deleted; totals are queries over `points_ledger` filtered by `week_start`.
- **Group weekly points** = sum of ledger points for that group and week.
- **Group bar target** = `100 * member_count` (about 4 good sessions per member). Bar fill = `min(100%, points / target)`.
- **Group leaderboard:** ranked by `weekly points / member_count` (per-member average), tie-break on current streak. Averaging stops 8-member groups beating 3-member groups on headcount alone.
- **Focus Tracker** results (section 9) never feed into any of these.
- **Individual ranking (inside a group only):** by weekly sum of `I` (improvement points), tie-break by completed sessions. Raw quiz scores are never compared across people or subjects.

### 1.6 Worked example

Ada (SS2) studies Chemistry, topic "Mole concept". Her last three Chemistry quizzes: 8/15, 9/15, 10/15 = 53.3%, 60.0%, 66.7%, so baseline = 60.0%.

She joins her group's 45-minute LIVE session on time, is active 41 minutes (`R` = 36 min, passes) and scores 11/15 = 73.3%.

| Component | Working | Points |
|---|---|---|
| B | round(45 / 3) | 15 |
| Q | round(73.3 / 10) | 7 |
| I | round((73.3 - 60.0) / 5) = round(2.67) | 3 |
| L | live, on time | 5 |
| **Total** | | **30** |

- Same session done SOLO: 25 points.
- v2: if all 4 members of her group complete this live session, each gets `G = +5`, so Ada gets 35.
- Her new Chemistry baseline is mean(60.0, 66.7, 73.3) = 66.7%.
- If this is her 4th completed session today: 0 points, but it still counts towards the streak.

## 2. Streak and freeze algorithm

**Rules:** the group streak increases by 1 for a Lagos day on which every eligible member completes at least one session (LIVE or SOLO). If not, a freeze is consumed automatically if available (2 per group per week; unused freezes do not roll over). A freeze keeps the streak at its current value (no increment, no points). With no freeze left, the streak resets to 0.

**Eligible member for day D:** joined before D 00:00 Lagos and still a member at D 23:59 Lagos. New members count from their first full day; members removed or leaving during D are ignored for D.

**Job:** APScheduler cron at **02:00 Lagos** daily, processing D = yesterday. 02:00 leaves room for a session started at 23:59 (60 min max + 30 min quiz window). The job is idempotent: `group_streak_days` has a unique key `(group_id, date)`.

```text
job nightly_streaks(now):
    D = lagos_date(now) - 1 day
    wk = monday_of(D)
    for group in active_groups():
        if exists group_streak_days(group.id, D): continue        # idempotent
        streak = group_streaks[group.id]
        members = eligible_members(group, D)
        if len(members) < 3:
            record(group, D, outcome="paused")                    # below min size: no change
            streak.last_evaluated_date = D                       # always advance the cursor
            continue
        done = { m for m in members
                 if exists completed participation with session_date == D }
        if done == members:
            streak.current += 1
            streak.best = max(streak.best, streak.current)
            outcome = "kept"
        elif streak.current > 0 and freezes_used(group, wk) < 2:
            insert streak_freezes(group.id, D, wk, reason="auto")
            outcome = "frozen"                                    # value unchanged
        else:
            streak.current = 0
            outcome = "broken"
        streak.last_evaluated_date = D
        record(group, D, outcome, completed=len(done), eligible=len(members))
    commit
    if D is Sunday: snapshot_weekly_leaderboard(wk)               # runs Monday 02:00
```

Judgement call: freezes are not spent on a streak that is already 0, so they are kept for when they matter. The cursor `last_evaluated_date` always advances after evaluating a day, including paused days, in the same transaction as its unique day record.

**Startup catch-up (decision, 15 Oct 2026):** convert now to Africa/Lagos. Before 02:00 today, the latest evaluable day is `today - 2`; from 02:00 onward it is `today - 1`. Iterate from `last_evaluated_date + 1` through that latest evaluable day, in order. Never finalise D before 02:00 Lagos on D + 1. No streak or freeze rules change.

## 3. Edge cases

### 3.1 Late join (LIVE)
- The server sets `scheduled_at`; the session starts at that time whether or not anyone is present, and ends at `scheduled_at + P`.
- Joining up to 10 minutes late: counts as LIVE and earns `L`. `R = 0.8 * (end_at - joined_at)`; `B` still uses the full `P`.
- Joining more than 10 minutes late: the client offers a SOLO session instead (same topic, own clock). The user can still sit in the room for presence, but gets no `L` and does not count towards the shared goal.

**Shared live goal (decision, 15 Oct 2026):** its denominator is the set of active group members at the live session’s scheduled start: `joined_at <= scheduled_at` and `left_at IS NULL OR left_at > scheduled_at`. Qualifying LIVE completions from those members count, including participation joins up to 10 minutes late. Members who join the group after the scheduled start are excluded. Later removals or departures do not shrink this historical denominator.

### 3.2 Leaving mid-session
- An explicit "Leave" stops the user's active clock. They may rejoin before `end_at`; active time accumulates.
- The quiz unlocks at the user's end time (`end_at` for LIVE, `started_at + P` for SOLO), or earlier for SOLO once `A >= R` and the user taps "Finish". If `A < R` at the end, the participation is `incomplete`: no quiz, no points, no streak credit.

### 3.3 Disconnects (grace period)
- The client sends a heartbeat every 15 s (over the WebSocket; SOLO sessions use the same socket).
- Active time: the gap between consecutive heartbeats is counted in full if it is <= 120 s (**grace period**, to forgive flaky mobile data), otherwise only 15 s of it counts.
- After 120 s with no heartbeat, presence shows "disconnected"; the user can reconnect any time before `end_at`.
- Tab focus is not required (people study from paper), but the PWA must be open.

### 3.4 Multiple groups
**Decision:** a user may be in up to 3 groups. One completed session counts for the **streak in every group** the user belongs to, and its `B + Q + I` is credited to **every group** (one ledger row per group). `L` and `G` are credited only to the group that hosted the live session.

**Justification:** studying is personal; making people choose a group or study twice would be penalising them for having more friends. Farming is not possible because the daily cap is per user, not per group, and groups are ranked per-member, so a member's identical contribution to each group is fair to all of them.

### 3.5 Member removed or leaves
- Only the group owner can remove members. Removal is effective immediately; the member is ignored for that day's streak (see eligibility).
- Ledger rows already earned stay (append-only history). This avoids "kick to protect the streak" disputes.
- If membership drops below 3, the streak is paused (not broken) until the group is back to 3.
- If the owner leaves, ownership passes to the longest-standing member.
- If the last member leaves, archive the group (`is_active = false`), disable its invites and retain membership history and ledger (decision, 15 Oct 2026).

### 3.6 Timezone
- Everything is computed with Africa/Lagos via `zoneinfo`, never the server's local time and never the client's. Users travelling abroad still use Lagos days (one shared clock for the group).
- Live session times are shown to clients as `scheduled_at` (UTC) plus `server_now` on the socket, so countdowns are corrected for device clock drift.

### 3.7 Quiz generation failure
Generation starts in the background when the session starts (plenty of time before the quiz unlocks). Order of attempts:
1. Cache hit for the key (3.8) that this user has not attempted before: use it, no LLM call.
2. LLM generation, 120 s timeout, validated; **one retry** with the validation errors appended.
3. Fallback: any cached quiz for the same `(subject_norm, level)` that the user has not attempted, labelled "related topic".
4. Still nothing: the participation is marked `quiz_status = unavailable`. It counts as **completed** on active time alone, earns `B` (and `L` if applicable) but no `Q` or `I`, and does not touch the baseline. Streaks are never broken by our infrastructure.

### 3.8 Cache and repeats
- Cache key: `sha256(subject_norm | topic_norm | level | prompt_version)`.
- Keep up to 5 variants per key. Serve one the user has not attempted; if all 5 are used, generate a new one (oldest is evicted).
- Ollama on a laptop handles one request at a time: use a single-worker asyncio queue, deduplicating jobs by cache key, so a group of 8 studying the same topic triggers one generation.

### 3.9 Bad questions (flags)
- Users can flag a question (reason: wrong answer, unclear, off-topic, inappropriate) after submitting.
- Flagging never changes the flagger's score (otherwise it becomes a cheat).
- At 3 flags from distinct users, or 1 "inappropriate" flag, the question is disabled and its quiz variant is retired from the cache.

### 3.10 Quiz integrity (light)
Correct answers are never sent to the client before submission. Options are shuffled server-side (LLMs over-use option A). One attempt per participation. The quiz timer runs for 20 minutes from its server-held start, and both starting and submitting must fit within 30 minutes of the participant end. Effective deadline: `min(quiz_start + 20 min, participant_end + 30 min)`.

Late submissions are rejected with a clear error. When `A >= R`, the session retains time-only completion and base points per the fallback rule, without quiz/improvement points or a baseline entry (decision, 15 Oct 2026).

## 4. Education level handling

`level` enum on `users` (editable in profile) and copied onto each **session participant** and quiz. The participant snapshot is the source of truth for quiz cache keys and baselines; `sessions` has no redundant level column (decision, 15 Oct 2026):

| Value | Prompt descriptor |
|---|---|
| `JSS1` to `JSS3` | Nigerian junior secondary year N (about age 10 to 14), NERDC curriculum / BECE style |
| `SS1` to `SS3` | Nigerian senior secondary year N, WAEC/NECO/JAMB UTME style |
| `UG_100` to `UG_500` | University undergraduate, Nth year (100L to 500L) |
| `POSTGRAD` | Postgraduate (Masters/PhD) |
| `OTHER` | General adult learner, intermediate difficulty |

Uses: (1) the `{level_descriptor}` in the LLM prompt; (2) part of the cache key; (3) part of the baseline key; (4) the group's audience band (section 8). Levels are self-declared; no proof is requested.

Sign-up at every university/postgraduate/OTHER level requires `18_plus` confirmation; JSS/SS requires guardian consent. Timestamps are server-held. No DOB, phone, photo or school name. |

Index (group_id, week_start), (user_id, lagos_date). |

## 6. API endpoints

Prefix `/api/v1`. Auth is a bearer JWT from fastapi-users unless marked public.

- `GET /users/me`, `PATCH /users/me` (display_name, level)

**Groups and invites**

- `POST /groups/{id}/sessions` (LIVE: `scheduled_at`, `planned_minutes`)

- `POST /sessions/{id}/leave` | `POST /sessions/{id}/finish` (SOLO early finish)

- `GET /groups/{id}/points?week=YYYY-MM-DD` (bar, per-member improvement ranking)

**WebSocket**
- `WS /ws/sessions/{id}?token=JWT`
  - Client -> server: `{"type":"heartbeat"}` every 15 s, `{"type":"react","emoji":"..."}` (fixed emoji set only).
  - Server -> client: `{"type":"state","server_now","started_at","end_at","status"}`, `{"type":"presence","members":[{user_id,display_name,status,subject}]}`, `{"type":"goal","done":n,"total":m}`, `{"type":"quiz_ready"}`, `{"type":"session_ended"}`.

## 7. LLM quiz generation

**Model:** a 7B to 8B instruct model in Ollama (for example `qwen2.5:7b` or `llama3.1:8b`), `temperature 0.4`, using Ollama's `format` parameter with the JSON schema below (structured output) and `stream: false`. Record `model_name` and `prompt_version` on each quiz.

### 7.1 Prompt template (`prompt_version = "v1"`)

```text
SYSTEM:
You are an experienced examiner writing multiple-choice questions for students.
Output only JSON that matches the provided schema. No commentary.

USER:
Write exactly 15 multiple-choice questions.
Subject: {subject}
Topic: {topic}
Learner level: {level_descriptor}

Rules:
- Every question must test the topic above at the stated level.
- Mix difficulty: 5 easy (recall), 6 medium (understanding), 4 hard (application).
- Each question has exactly 4 options, all different, all plausible.
- Exactly one option is correct; give its index (0 to 3) as correct_index.
- Do not use "all of the above", "none of the above" or "both A and B".
- Keep each question under 300 characters and each option under 120 characters.
- Add a one-sentence explanation (under 200 characters) of the correct answer.
- Use British English and examples familiar to Nigerian students where natural.
- Content must be suitable for school-age learners.
{retry_feedback}
```

`{retry_feedback}` is empty on the first attempt; on retry it is: `Your previous answer was invalid: {errors}. Fix these problems and return all 15 questions.`

### 7.2 JSON schema

```json
{
  "type": "object",
  "required": ["questions"],
  "properties": {
    "questions": {
      "type": "array",
      "minItems": 15,
      "maxItems": 15,
      "items": {
        "type": "object",
        "required": ["question", "options", "correct_index", "explanation", "difficulty"],
        "properties": {
          "question":      {"type": "string", "minLength": 10, "maxLength": 300},
          "options":       {"type": "array", "minItems": 4, "maxItems": 4,
                            "items": {"type": "string", "minLength": 1, "maxLength": 120}},
          "correct_index": {"type": "integer", "minimum": 0, "maximum": 3},
          "explanation":   {"type": "string", "maxLength": 200},
          "difficulty":    {"type": "string", "enum": ["easy", "medium", "hard"]}
        }
      }
    }
  }
}
```

### 7.3 Validation (server-side, Pydantic, after parsing)

1. Valid JSON matching the schema; exactly 15 questions.
2. Exactly 4 options per question, **distinct** after normalisation (lowercase, trim, collapse spaces, strip trailing punctuation).
3. Exactly **1 correct** answer: `correct_index` in 0 to 3, and the correct option text appears only once.
4. No banned options ("all/none of the above", "both ... and ...").
5. No duplicate questions within the quiz (normalised text).
6. Basic content filter: a small blocklist of profanity and adult terms; any hit fails the quiz.
7. On failure: **retry once** with the error list. Second failure: fallback path (3.7). Never show a partially valid quiz.
8. On success: shuffle options and recompute `correct_index`, then store as a new `quizzes` variant.

## 8. Safety note: under-18 and university users

- **Two audience bands.** Users at JSS/SS levels are `secondary` (assumed under 18); 100L and above and `OTHER` are `tertiary` (university/adult band). Users selecting any university/postgraduate/OTHER level must confirm they are 18+, recorded as `age_band = 18_plus` and `adult_confirmed_at` (step 3 decision). No cross-band groups are allowed. A group's band is set from the creator's level, and only users of the same band can join it. Under-18s and adults are therefore never in a group together. The group leaderboard is also split by band. (Judgement call: this blocks a university sibling tutoring a secondary student inside the app; acceptable for v1.)
- **Data minimisation.** Collect only email, password hash, display name and level. No date of birth, phone number, photo, school name or location. Display names are shown to group members only; there are no public profiles or search.
- **Invite-only.** Groups cannot be discovered; joining needs a code or link that expires after 7 days and can be revoked. The public invite preview shows only the group name and member count.
- **No free-text chat in v1.** Presence and a fixed set of emoji reactions only, so there is nothing to moderate between members. Flag notes are seen only by the operator.
- **Consent.** The Nigeria Data Protection Act 2023 treats under-18s as children whose data needs parent or guardian consent. For the hackathon, show a guardian-consent confirmation at sign-up for secondary levels and record `guardian_consent_at`; take proper legal advice before a real launch.
- **LLM content.** The model runs locally, so no study data leaves the server. Prompts require school-suitable content, the output is filtered, and a single "inappropriate" flag removes the question.
- **Camera (Focus Tracker).** Opt-in per session, off by default, processed on the device only; only a numeric summary is stored (section 9).
- **Deletion.** `DELETE /users/me` removes the profile and anonymises ledger and attempt rows (user_id replaced by a tombstone) so group totals stay consistent. **TODO:** replacing ledger user IDs conflicts with the append-only rule in section 5. Resolve the anonymisation strategy before exposing account deletion; the current schema does not permit ledger rewrites.

## 9. Focus Tracker (opt-in)

**Placement:** v2. For the hackathon it is a stretch goal; a minimal version is in 9.13. It is a self-reflection tool, not an exam proctor.

### 9.1 Ground rules

1. **Opt-in per session, off by default.** The toggle sits on the join screen and is unticked every time.
2. **On-device only.** All video is processed in the browser. No video, frames, images, landmarks or face data leave the device. Only the numeric summary in 9.8 is sent.
3. **No stakes.** The focus score never affects points, streaks, the shared goal, the group bar or any leaderboard. The scoring and streak code must not read `focus_summaries`.
4. **Comparison only after the session, anonymous, and only with 3 or more.** The user sees their own score. They see how they compare with other opted-in participants of the **same session** only after that session has ended, and only if at least 3 participants (including them) opted in and sent a valid summary. Otherwise they see their personal score only. Other people's scores are never shown individually or with names, and there is no live ranking.

### 9.2 Library choice (checked 15 Oct 2026)

The `*Left`/`*Right` blendshapes refer to the subject's face, and a mirrored input swaps them. Serve the WASM files and the `face_landmarker.task` model bundle from our own origin, not a CDN. The library code is Apache-2.0; check the model cards linked from the overview page for the model bundle's own terms before launch.

### 9.3 Pipeline

- `getUserMedia({video: {width: 320, height: 240, facingMode: "user"}})`. Low resolution is enough and saves CPU.
- Face Landmarker in `VIDEO` mode inside a Web Worker, with `numFaces: 1`, `outputFaceBlendshapes: true` and `outputFacialTransformationMatrixes: true`.
- Sample at **1 fps** (2 fps if calibration shows the device has headroom). Each sample is turned into a few booleans straight away; the frame and landmarks are thrown away.
- Pause while the tab is hidden and resume when it is visible again. Stop all camera tracks at session end, on Leave, or when the user taps Stop.
- No recording APIs, no canvas export, no network calls from the worker.

### 9.4 Signals per sample

| Signal | Source | Rule (defaults, tunable) |
|---|---|---|
| `face_present` | a face is returned (default presence confidence 0.5) | true or false |
| Head yaw / pitch | angles taken from the facial transformation matrix, minus the calibrated neutral `(yaw0, pitch0)` | `head_ok` if `abs(yaw) <= 30°` and `-45° <= pitch <= +20°` (negative = looking down) |
| Eyes closed | mean of `eyeBlinkLeft` and `eyeBlinkRight` blendshapes | `eyes_closed` if mean > 0.5; only counts against you if it lasts 3 or more consecutive seconds (dozing) |
| Gaze off-screen (optional, v2) | `eyeLookOut*`/`eyeLookIn*` blendshapes | off by default; unreliable on cheap webcams and when looking at paper |

**Blink rate is not used.** A blink lasts a fraction of a second, so it cannot be counted reliably at 1 to 2 fps. Sustained eye closure is used instead.

`attentive(sample) = face_present AND head_ok AND NOT sustained_eyes_closed` (`AND NOT gaze_off` only if gaze is enabled).

### 9.5 Legitimate look-aways

- **Looking down at paper or notes is attentive.** The pitch window allows 45° down from the calibrated neutral position.
- **Short breaks are forgiven.** After sampling, any non-attentive run of 5 s or less with the face present is relabelled attentive (glancing aside, stretching).
- **Away rule:** a face-absent run of up to `N = 20 s` is relabelled attentive (reaching for a book, leaning out of frame). A face-absent run **longer than 20 s** counts as away for its whole length and adds to `away_seconds`.
- **Paused time** (tab hidden, camera stopped by the user) is not counted either way. It is reported as `paused_seconds` and shown to the user.

### 9.6 Score

```text
valid_samples   = samples taken while the tracker was running (excludes paused time)
attentive_pct   = round(100 * attentive_samples / valid_samples)     # 0 to 100
coverage        = valid_seconds / active_seconds_of_participation
valid_summary   = coverage >= 0.5 AND valid_samples >= 60
```

Worked example: a 45-minute session sampled at 1 fps with 2,580 valid samples. There are 2,322 attentive samples after the forgiveness rules, and two away runs of 90 s and 60 s. Result: `attentive_pct = 90`, `away_seconds = 150`.

A summary that is not valid is still shown to the user as "Not enough camera data" and is left out of the comparison.

### 9.7 Calibration (about 10 s at session start)

1. Copy: "Sit how you'll study. Look at the screen, then at your notes."
2. Record the median yaw and pitch while looking at the screen as `(yaw0, pitch0)`.
3. Check a face is found in at least 80% of frames. If not: "We can't see your face clearly. Try more light in front of you, or turn Focus Tracker off." The user can retry or skip.
4. Measure the mean `detectForVideo` time to decide the frame rate (9.8).

### 9.8 Low-end devices

- **Disable** with the message "Focus Tracker isn't available on this device" if WebGL/WASM fails to load or the mean detection time during calibration is over 500 ms.
- **Choose the rate:** 2 fps if the mean is under 100 ms, otherwise 1 fps.
- **Back off during the session:** if 3 samples in a row take over 1 s, drop to 0.5 fps. If that is still too slow, stop the tracker and send a partial summary, which is usually not valid.
- Where the Battery Status API exists (Chromium browsers), suggest turning it off when the battery is under 20% and not charging.

### 9.9 Comparison rules (server)

- Available only when `session.status = ended` and the summary window (session end + 30 min) has closed, so nobody's result depends on submission order.
- Comparison set = valid summaries from opted-in participants of that one session. If there are fewer than 3, return personal only.
- The response gives the user's own score, the number of comparable participants `n`, the **session median**, and their position: `above` (more than 5 points over the median), `around` (within 5 points) or `below`. No other individual scores, names or ranks are returned.
- SOLO sessions have one participant, so they always show personal only.
- Judgement call: in a group of 3 the median is one person's actual score. That is acceptable because it carries no name and no stakes, but the UI must not show the opted-in member list next to the result.

### 9.10 Privacy UX copy

- **Join toggle (off):** "Focus Tracker (optional). Uses your camera to estimate how focused you were. Video stays on this device; only a score is saved."
- **Info sheet:** "Your camera is processed by this browser only. We never record, upload or store video or images. After the session we save a few numbers (focus %, time away, number of checks). It never changes your points or streak. You can stop it at any time."
- **While running:** small pill "Camera on, processed on this device" with a **Stop** button (the browser's own camera indicator also shows).
- **Result card:** "You were focused 90% of the time. That's above the session median (4 people opted in)." Or, with fewer than 3: "You were focused 90% of the time. Not enough people opted in to compare."
- Neutral wording only: no "lazy" or "distracted"; "time away" rather than "caught".

### 9.11 Under-18 users

- The guardian consent taken at sign-up for secondary levels (section 8) covers this feature, and its wording must mention the optional on-device camera feature.
- It is still off by default in every session. Judgement call: secondary-band users get no "remember my choice" option, so they opt in fresh each time. Tertiary users may save it as a preference.
- Comparisons only ever involve the same session, which is in the same audience band by design.

### 9.12 Data model and API additions

**Table `focus_summaries`**

| Column | Type | Notes |
|---|---|---|
| `id` | int PK | |
| `session_participant_id` | FK session_participants, unique | one per participation |
| `opted_in` | bool | false rows have null metrics (records the choice only) |
| `attentive_pct` | int, null | 0 to 100 |
| `away_seconds` | int, null | |
| `samples` | int, null | valid samples |
| `paused_seconds` | int, null | extra |
| `sample_fps` | real, null | extra (0.5, 1 or 2) |
| `is_valid` | bool | computed server-side from coverage (9.6) |
| `tracker_version` | text | for example `mp-1.1.1/v1` |
| `created_at` | UTC timestamp | |

Retention: 90 days, then delete. Removed by `DELETE /users/me`. Server sanity checks: `0 <= attentive_pct <= 100`, `samples <= 2 * duration_seconds + 30`, `away_seconds <= duration_seconds`. Values are self-reported and can be faked; that is acceptable because nothing rides on them.

**Endpoints**

- `POST /participants/{id}/focus-summary`, body `{opted_in, attentive_pct, away_seconds, samples, paused_seconds, sample_fps, tracker_version}`. Owner only, once per participation (409 on repeat), accepted until session end + 30 min.
- `GET /sessions/{id}/focus-comparison`. For participants of that session only; 409 until the window in 9.9 has closed. Returns `{"mine": {"attentive_pct": 90, "away_seconds": 150, "is_valid": true}, "comparison": {"n": 4, "median_pct": 82, "position": "above"}}`, with `comparison: null` when n < 3.
- The WebSocket never carries focus data.
